# Как всему научиться и сделать самостоятельно

Учебный компаньон к `roadmap.md`: какие навыки нужны на каждой фазе, где их
брать и как работать над фичей без ассистента. Цель — не «пройти курсы», а
**научиться в процессе постройки**: каждая фаза roadmap = учебный модуль.

---

## 1. Метод: как учиться, чтобы прилипало

1. **Фича — сначала, теория — после первой попытки.** Порядок: попробовал сам
   (30–60 мин) → упёрся → прочитал доку по конкретному вопросу → доделал.
   Чтение доки «впрок» без задачи выветривается за неделю; чтение после
   собственной боли запоминается навсегда.
2. **Одна новая технология за раз.** Фаза 6 вводит Zustand + Router + новую
   структуру — поэтому в ней запрещены новые фичи. Никогда не изучай библиотеку
   на задаче, где и без неё сложно.
3. **Заметки-шпаргалки своими словами.** После каждой фазы — 10–15 строк в
   `notes/` (или в этот файл): что понял, что удивило, какую ошибку словил.
   Формулирование = половина усвоения. REVIEW.md уже работает так — продолжай.
4. **Читай чужой код.** Открой исходники маленьких библиотек, которые используешь:
   Zustand — ~400 строк ядра, clsx — 50 строк. Понимание «магии» убирает страх.
5. **Правило 15 минут** для затыка: 15 минут бьёшься сам → формулируешь вопрос
   письменно (часто ответ приходит при формулировании — «резиновая уточка») →
   ищешь в доке/GitHub issues → только потом спрашиваешь ассистента/форум.
6. **Самопроверка после темы** — ответь вслух без подглядывания. Не смог —
   тема не закрыта. Вопросы даны в конце каждого модуля ниже.

## 2. Карта навыков по фазам

### Модуль A — React-фундамент (фазы 0–1)

**Темы:** управляемые инпуты; производное состояние vs хранимое; иммутабельные
обновления массивов/объектов; поднятие и колокация state; формы и события.

**Ресурсы:**
- [react.dev/learn](https://react.dev/learn) — блок «Managing State» целиком
  (есть перевод: ru.react.dev). Это главный учебник, курсы не нужны.
- Статья «You Might Not Need an Effect» на react.dev — обязательна: закрывает
  главную ошибку джунов (синхронизация состояния через useEffect).
- [learn.javascript.ru](https://learn.javascript.ru) — если проседает сам JS
  (методы массивов, деструктуризация, замыкания, промисы).
- [doka.guide](https://doka.guide) — справочник по вебу на русском, хорош по CSS/HTML.

**Проверь себя:** почему `filteredTasks` нельзя класть в useState? чем
`setTasks(tasks.filter(...))` отличается от `setTasks(prev => prev.filter(...))`
и когда это важно? почему `defaultChecked` сломал чекбокс?

### Модуль B — TypeScript всерьёз (фазы 2 и 6.1)

**Темы:** union/discriminated union; `type` vs `interface`; generics на уровне
чтения; сужение типов (`narrowing`); типизация событий и пропсов.

**Ресурсы:**
- [TypeScript Handbook](https://www.typescriptlang.org/docs/handbook/) — разделы
  Everyday Types, Narrowing, Object Types. Не читать целиком — по мере нужды.
- [Total TypeScript](https://www.totaltypescript.com/tutorials) — бесплатные
  интерактивные туториалы Мэтта Покока (Beginners TypeScript — то, что нужно).
- [React TypeScript Cheatsheet](https://react-typescript-cheatsheet.netlify.app) —
  держать открытым при типизации компонентов.

**Проверь себя:** почему action'ы reducer'а — discriminated union и что даёт
поле `type`? как TS понимает внутри `case "rename":`, что у action есть `title`?

### Модуль C — Состояние: reducer → Zustand (фазы 2, 6.2)

**Темы:** reducer как чистая функция; селекторы; нормализация данных;
слайсы; persist и миграции.

**Ресурсы:**
- react.dev → «Extracting State Logic into a Reducer» и «Scaling Up with
  Reducer and Context» — мост от фазы 2 к фазе 6.
- [Официальная дока Zustand](https://zustand.docs.pmnd.rs) — короткая, читается
  за вечер. Разделы: slices pattern, persist middleware, practice with no store actions.
- Блог [TkDodo](https://tkdodo.eu/blog/) — «Working with Zustand» и вся серия
  про React Query (пригодится в фазе 12). Лучший блог о state-менеджменте.
- Redux-дока, раздел [Normalizing State Shape](https://redux.js.org/usage/structuring-reducers/normalizing-state-shape) —
  сам Redux не нужен, но объяснение нормализации там каноническое (это про 6.1).

**Проверь себя:** почему подзадачи — `parentId`, а не массив внутри эпика?
что перерисуется при `useStore(s => s.tasks)` против
`useStore(s => s.tasks.find(t => t.id === id))`? зачем persist'у `migrate`?

## 3. Алгоритм самостоятельной работы над фичей

Каждый пункт roadmap проходи по одному конвейеру:

1. **Сформулируй результат** одним предложением: «пользователь может X».
   Запиши 2–3 acceptance-критерия (что кликаю → что вижу).
2. **Продумай данные до UI**: какие поля/сущности нужны? что хранится, что
   вычисляется? нужна ли миграция persist? Набросай типы TS — они дешевле кода.
3. **Ветка** `feat/<название>` (см. REVIEW.md → Практики).
4. **Вертикальный срез, а не слоями**: сначала грубая версия фичи целиком
   (store action + минимальный UI без стилей), потом улучшение. Не «сначала весь
   стор, потом весь UI» — интеграционные проблемы должны всплыть рано.
5. **Тест на логику** сразу после action/селектора, пока помнишь граничные случаи.
6. **Стили и состояния**: пустое, загрузка (если будет API), ошибка, длинный
   текст, оверфлоу. Прогон клавиатурой: Tab, Enter, Escape.
7. **Self-review диффа** перед merge — читай свой PR как чужой: убраны console.log?
   имена по конвенции? нет дублирования с существующими утилитами? комментарии
   объясняют «почему», а не «что»?
8. **Чек перед merge**: `npm run lint && npx tsc -b && npm test` + ручной happy path.
9. **Заметка**: 3 строки — что нового узнал, где споткнулся.

## 4. Когда застрял

1. Прочитай сообщение об ошибке **целиком, до конца** — ответ там в 60% случаев.
2. Минимальный репро: вынеси проблему в отдельный компонент/файл на 20 строк.
   Пока выносишь — обычно находишь причину.
3. `console.log` / React DevTools (вкладка Components → props/state) /
   отладчик с брейкпоинтом — смотри, что **на самом деле** в данных, а не что
   ты думаешь, что там.
4. Git — твоя машина времени: `git stash` / `git diff` — что изменилось с
   момента, когда работало?
5. Ищи по точному тексту ошибки в кавычках + имя библиотеки; смотри GitHub
   issues библиотеки, не только StackOverflow.
6. Не решилось за час — оставь вопрос записанным и переключись на другой пункт
   фазы. Утренняя голова решает за 10 минут то, что вечерняя не решила за два часа.

## 5. Как использовать ассистента экономно (когда подписка вернётся)

Дорого и бесполезно для обучения: «напиши мне фичу X целиком».
Дёшево и полезно:
- **Ревью**: «вот дифф, найди проблемы» — учишься на своём коде (+ запись в REVIEW.md).
- **Объяснение после попытки**: «я сделал так, работает, но выглядит криво — почему и как принято?»
- **Разбор непонятного**: «объясни это сообщение об ошибке / этот кусок доки».
- **Спарринг по архитектуре до кода**: «вот моя модель данных для фичи X, что я упустил?»
- Один вопрос = один конкретный кусок. Roadmap уже нарезан на такие куски — 
  копируй раздел как контекст.
